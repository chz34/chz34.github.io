01 · 三段式总览与数据流

torch.compile 不是一个单体编译器，而是三个子系统的流水线。每一段接收上一段产出的图，做自己的变换后交给下一段。对做 runtime 的人来说，最关键的认知是：这三段之间流动的"图"，格式和语义各不相同。

图 1.1 — torch.compile 三段式流水线。方框之间流动的是不同格式的图。

  • Dynamo（torch/_dynamo）：在 CPython 字节码层拦截执行，把一段可追踪的代码捕获成一个 torch.fx.GraphModule。图里的节点是用户层 torch 算子（torch.matmul、torch.relu…）。遇到无法追踪的东西就 "graph break"，切成多段。
  • AOTAutograd（torch/_functorch/aot_autograd.py）：把前向 trace 到 ATen 层，用 autograd 展开出反向，合并成一张 joint graph，再 partition 成 forward / backward 两张图。此时算子已经是functional、去糖化的 ATen core opset。
  • Inductor（torch/_inductor）：官方默认后端。对 ATen FX 图做 post-grad 优化，lower 成自己的 Inductor IR，交给 Scheduler 做融合与排序，最后 codegen 出 Triton / C++ kernel 加一段 wrapper 胶水代码。
给 runtime 开发者的定位提示 你有两个天然的介入边界：(A) 拿 AOTAutograd 产出的 functional ATen FX 图，完全绕开 Inductor，自己写编译/运行时（torch.compile(backend=…) 或 torch.export）；(B) 留在 Inductor 内部，只替换设备相关的 Scheduling / Wrapper / kernel codegen（register_backend_for_device）。两条路线第 14 节详细对比。

02 · 贯穿全文的示例模型

为了让"每个阶段的图"具体可见，全文用同一个极小模型追踪到底：

import torch, torch.nn as nn

class Tiny(nn.Module):
    def __init__(self):
        super().__init__()
        self.w = nn.Parameter(torch.randn(512, 512))
    def forward(self, x):                # x: f32[128, 512]
        return torch.relu(x @ self.w + 1.0)

model = Tiny().cuda()
opt = torch.compile(model)              # backend="inductor"（默认）
y = opt(torch.randn(128, 512, device="cuda"))

代码 2.1 — 一个 matmul + bias + relu 的小模型。下面每节都会给出它在该阶段的图形态。

它只有三步计算：一次矩阵乘、一次加常数、一次 ReLU。看似平凡，但它恰好覆盖了 Inductor 两类核心处理——矩阵乘走 template / extern kernel 路线，而 add + relu 是可融合的 pointwise 逐元素运算。这两类的差异贯穿后文。

03 · Dynamo：字节码到 FX（简介）

Dynamo 的职责只有一件事：把 Python 函数体安全地捕获成一张 FX 图。它通过 PEP 523 的 frame evaluation hook 接管字节码执行，做符号化追踪，把张量运算记录成 FX 节点，把控制流、外部副作用等无法追踪的部分作为 graph break 保留在 Python 里。

对我们的示例，Dynamo 交给后端的图大致是：

class GraphModule(torch.nn.Module):
    def forward(self, L_x_: "f32[128, 512]", L_self_w: "f32[512, 512]"):
        matmul = torch.matmul(L_x_, L_self_w)      # call_function, target=torch.matmul
        add    = matmul + 1.0                    # target=operator.add
        relu   = torch.relu(add)                   # target=torch.relu
        return (relu,)

代码 3.1 — Dynamo 产出的 torch-IR FX 图（representative）。算子仍是用户层 torch / operator 调用。

别把这张图当接管点 Dynamo 图的算子是用户层、非 functional、未去糖的（torch.matmul 而非 aten.mm；bias 加法可能是 operator.add）。它没有反向、没有做 decomposition，opset 不稳定。做 runtime 一般不在这里接管，除非你只要推理且愿意自己补齐 decomposition。

04 · AOTAutograd：joint 图与分割（简介）

AOTAutograd 接过 Dynamo 的图，做三件事，产出一对真正"干净"的图：

  1. trace 到 ATen 并 functionalize：把 torch 算子降到 ATen core opset，消除 in-place / view 别名，使图变成纯函数式（no mutation）。
  2. 用 autograd 展开反向、构建 joint graph：前向 + 反向合并到一张图里，这是唯一能同时看到 fwd/bwd 的阶段。
  3. partition：默认用 min_cut_rematerialization_partition 决定哪些激活值保存、哪些重算，切成 forward / backward 两张 GraphModule，分别交给 fw_compiler / bw_compiler（即 Inductor 的编译入口）。

→
trace + functionalize→ ATen, 无别名
→
joint graphfwd + bwd 合并
→
partitionmin-cut 重物化
→
fw / bw 图functional ATen
→ 交给 Inductor

图 4.1 — AOTAutograd 内部数据流。fw_compiler 收到的就是右端的 forward 图。

示例（推理场景无反向）的 forward 图，也就是 Inductor 真正拿到的那张图：

def forward(self, primals_1: "f32[512, 512]", primals_2: "f32[128, 512]"):
    mm   = torch.ops.aten.mm.default(primals_2, primals_1)   # f32[128, 512]
    add  = torch.ops.aten.add.Tensor(mm, 1.0)              # f32[128, 512]
    relu = torch.ops.aten.relu.default(add)                  # f32[128, 512]
    return (relu,)

代码 4.1 — post-AOTAutograd 的 functional ATen forward 图（representative）。参数以 primals_N 形式作为 placeholder 输入。

注意与 Dynamo 图的关键差异：torch.matmul 变成了 aten.mm.default（带 overload 后缀的 OpOverload），参数 self.w 不再是 get_attr 而是被提升成了输入 placeholder（primals_1）。这一点对做 runtime 很重要——见第 5 节的 "stateless" 讨论。

05 · 你到底拿到哪张 FX 图

"我拿到的是哪张图"是 runtime 开发者最容易含糊的地方。整个流水线里存在至少四张形态不同的 FX 图，取决于你在哪注册 backend：

图产出者opset特征 / 你能拿到它的方式
Dynamo 图Dynamotorch / python ops非 functional、无反向、含 get_attr。torch.compile(backend=fn) 的 最外层 自定义 backend 会看到它（若不接 aot_autograd）。
joint 图AOTAutogradfunctional ATenfwd+bwd 合并。只有自定义 partition_fn 能看到，一般不作为运行接管点。
fw / bw 图AOTAutograd partitionfunctional ATen core分离的前/反向，参数已提升为输入（stateless）。aot_autograd 的 fw_compiler/bw_compiler 收到它——这是最推荐的接管点。
post_grad 图Inductorfunctional ATen（已优化）在 fw/bw 图上又跑了 pattern match、融合等 pass。Inductor GraphLowering 遍历的就是它。
ExportedProgramtorch.exportATen core（稳定）AOT、静态、带 state_dict 与签名。官方承诺稳定的"编译器接口"。做独立工具链时首选。
"stateless" 是关键性质 在 fw/bw 图及其之后，模型参数与 buffer 已经作为 placeholder 输入节点存在（示例里的 primals_1 就是 self.w），图里不再有 get_attr 引用外部状态。这意味着你的 runtime 只要按输入顺序喂 tensor 即可，无需理解 nn.Module 的层级——外部编译器（如 torch-mlir 的 stateless_fx_import）正是利用这一点直接消费 Dynamo/AOT 图。

如何注册一个能观察这些图的最外层 backend：

from torch._dynamo import register_backend

@register_backend
def my_backend(gm: torch.fx.GraphModule, example_inputs):
    # gm 是 Dynamo 图（torch ops）。example_inputs 是 FakeTensor 列表。
    gm.graph.print_tabular()          # 打印节点表，快速看清图结构
    return gm.forward                  # 返回一个可调用；这里先退化为 eager

opt = torch.compile(model, backend="my_backend")

代码 5.1 — 最外层自定义 backend 的骨架。要拿 functional ATen 图，用下方 aot_autograd 包一层。

from torch._functorch.aot_autograd import aot_autograd

def my_compiler(gm, example_inputs):
    # 此处 gm 已是 functional ATen 的 fw 或 bw 图
    for node in gm.graph.nodes:
        ...                            # 解析并编译到你的硬件（见第 6 节）
    return gm.forward

my_backend = aot_autograd(fw_compiler=my_compiler, bw_compiler=my_compiler)
opt = torch.compile(model, backend=my_backend)

代码 5.2 — 用 aot_autograd 包裹，让你的 compiler 收到分离后的 functional ATen 图。

06 · 如何解析 FX node 的信息

拿到 gm.graph 后，一切信息都挂在 torch.fx.Node 上。一个 node 有五个核心字段，先建立结构认知：

字段含义
node.op节点类型：placeholder（输入）/ call_function / call_method / call_module / get_attr / output。
node.target被调用的东西。对 ATen 图是 OpOverload（如 torch.ops.aten.mm.default）；placeholder 时是输入名字符串。
node.args / node.kwargs调用实参。元素多为其它 Node（表示数据依赖），也可能是常量（标量、shape 列表等）。
node.meta元数据字典——解析 shape/stride/dtype/device 的金矿。见下。
node.users下游消费者（dict[Node, None]），用来分析生命周期与死代码。

6.1 从 node.meta['val'] 抠出全部张量信息

AOTAutograd/Inductor 在 trace 时会把每个节点的输出用 FakeTensor（无真实数据、只有元信息的张量）填进 node.meta['val']。它就是一个 torch.Tensor 的"影子"，支持全部形状查询 API：

from torch.fx.experimental.symbolic_shapes import free_symbols

def describe(node):
    val = node.meta.get("val")          # FakeTensor（或 SymInt / list[FakeTensor]）
    if isinstance(val, torch.Tensor):
        info = {
            "shape":  tuple(val.shape),     # 可能含 SymInt（动态维）
            "stride": tuple(val.stride()),  # 内存步长——布局的核心
            "dtype":  val.dtype,            # torch.float32 ...
            "device": val.device,           # device(type='cuda', index=0)
            "offset": val.storage_offset(),
            "contig": val.is_contiguous(),
            "dynamic": bool(free_symbols(val.shape)),  # 是否有符号维
        }
        return info

代码 6.1 — 从任意节点解析完整张量元信息。stride 决定你在设备上如何寻址；device 告诉你该把 buffer 放哪。

还有一个 tensor_meta 除了 val，经过 ShapeProp 的图里每个节点还可能带 node.meta['tensor_meta']——一个 TensorMetadata namedtuple（shape / dtype / requires_grad / stride / memory_format / is_quantized / qparams）。它是纯静态快照，序列化友好；而 val（FakeTensor）能力更强、能表达符号维。两者都读，优先 val。

6.2 遍历整张图并区分节点角色

for node in gm.graph.nodes:
    if node.op == "placeholder":
        # 图输入：参数、激活、动态 shape 的符号。按出现顺序对应运行时实参。
        register_input(node.name, describe(node))
    elif node.op == "call_function":
        op   = node.target                     # OpOverload
        name = op._schema.name                 # "aten::mm"
        # node.target._schema 给出完整签名：参数名、类型、是否 mutable、alias 信息
        emit_op(op, node.args, node.kwargs, out=describe(node))
    elif node.op == "get_attr":
        # 图内常量/参数（fw/bw 图里通常已无此类；export 图里可能有）
        const = getattr(gm, node.target)
    elif node.op == "output":
        # node.args[0] 是输出（tuple of Node），确定返回顺序与别名
        bind_outputs(node.args[0])

代码 6.2 — 一次遍历即可把图转成你自己的算子序列。args 里的 Node 引用天然给出数据依赖（DAG 边）。

从 schema 拿到算子的"契约" node.target 是 OpOverload，它的 ._schema 是解析算子语义的权威来源：参数名与类型、返回数、is_mutable、alias 集合。你无需为每个 aten 算子硬编码，读 schema 就能自动生成参数绑定。若某算子你的硬件不支持，可通过 decomposition（torch._decomp）把它拆成更基础的算子——Inductor 内部也大量依赖 decomposition table 把 opset 收窄。

07 · Inductor 入口与编排

从这里开始进入 Inductor 内部。编译入口是 compile_fx（torch/_inductor/compile_fx.py），它并不直接编译，而是把 pre-grad / partition 回调注入 aot_autograd，真正的编译主体在 codegen_and_compile() 里闭环完成。层次如下：

compile_fx()公开入口：config_patches、cpp_wrapper 分支
↓
_compile_fx_main()注入 pre_grad / partition 回调，调用 aot_autograd
↓
aot_autograd 内部pre_grad passes → joint graph → joint passes + partition → fw/bw compiler 回调
↓
codegen_and_compile()③ post_grad passes → ④ GraphLowering.run() → ⑤ Scheduler + codegen

图 7.1 — 编译编排。前两个阶段以回调形式在 AOTAutograd 里执行，后三个阶段在 Inductor 自身闭环内。

你几乎不需要改这层。重点记住：Inductor 真正开始工作是在 codegen_and_compile()，它先跑 post_grad passes（fx_passes/post_grad.py，functional ATen 上最稳定的 FX 优化阶段），再构造 GraphLowering 并 run()。

08 · Lowering：FX → Inductor IR

Lowering 是 Inductor 特有的一步：把 ATen 的 FX 图 翻译成 Inductor 自己的 IR 节点树。做这件事的是 GraphLowering（torch/_inductor/graph.py），它继承自 torch.fx.Interpreter——也就是说，它用解释器模式逐节点"执行"FX 图，但每一步产生的不是张量，而是 IR 节点。

8.1 placeholder → InputBuffer（附带 Layout）

输入节点被翻译成带 FixedLayout 的 InputBuffer，Layout 精确记录 device / dtype / sizes / strides：

# graph.py :: GraphLowering.placeholder（节选）
if not example._has_symbolic_sizes_strides:
    sizes, strides = self.static_sizes_strides(example)      # 静态 shape
    storage_offset = sympy.Integer(example.storage_offset())
else:
    sizes, strides, storage_offset = \
        self.symbolic_sizes_strides_storage_offset(example)  # 动态 shape → sympy 符号

tensor = TensorBox.create(
    InputBuffer(
        name=target,
        layout=FixedLayout(example.device, example.dtype, sizes, strides),
    )
)
self.graph_inputs[target] = tensor
self.graph_input_names.append(target)

代码 8.1 — 输入 lowering。注意 sizes/strides 用 sympy 表达式承载，动态维是符号，静态维是整数。这与你 runtime 里描述 buffer 的方式高度对应。

对齐（alignment）不 guard 同一段代码里，Inductor 会根据 example 输入是否对齐决定是否走向量化 load，但不对 storage_offset 加 guard（guard 太贵会引发 recompile）。未对齐的输入会被登记到 unaligned_buffers。做硬件 runtime 时同理：要么按 example 对齐假设生成、运行时不满足则 clone，要么显式处理非对齐——这是一个性能/正确性的经典权衡点。

8.2 call_function → 查 lowering 表 → 生成 IR

每个 call_function 节点触发 GraphLowering.call_function()，它按优先级查找该 aten 算子的 lowering 规则：

# 概念化的查找链（graph.py + lowering.py）
if target in user_lowerings:   # 用户自定义（最高优先级）
    out = user_lowerings[target](*args, **kwargs)
elif target in lowerings:    # 内置 lowering 表
    out = lowerings[target](*args, **kwargs)
else:                          # 兜底：生成 FallbackKernel（直接调 ATen 实现）
    out = fallback_handler(target)(*args, **kwargs)

代码 8.2 — lowering 优先级。找不到规则就 fallback 到调用 eager ATen 算子（对 mm 这类通常走 extern kernel）。

示例里，aten.add 与 aten.relu 走 pointwise lowering，产出 Pointwise 节点；aten.mm 通常不 lower 成 loop，而是走 ExternKernel / template（调 cuBLAS 或 Triton matmul 模板）。

图 8.1 — 从外到内：TensorBox → StorageBox → ComputedBuffer → Loops。ExternKernel / FallbackKernel 是并列的另一支（不走 loop，直接调库）。

IR 类角色
TensorBox / StorageBox可变盒子（MutableBox），把"张量"与"存储"解耦，支持 in-place 改写与 realize。
Loops → Pointwise / Reduction核心：用一个 inner_fn(index) → 值 闭包 + ranges（循环维度）描述计算，不落地。
ComputedBuffer把 Loops 绑定到一个 Layout，成为可被写入的具体缓冲。
Layout / FixedLayout / FlexibleLayout描述内存布局：device、dtype、size、stride、offset。Flexible 允许 Inductor 后续改 stride（如转 channels-last）。
ExternKernel / FallbackKernel不生成 loop、直接调外部实现（cuBLAS、aten 兜底）的算子。matmul、conv 常走这里。
两条设计原则，直接决定 Inductor IR 好不好被你消费 懒求值：Pointwise 等是计算的描述而非执行，只有 realize() 才真正分配 buffer。Scheduler 因此能在"不算任何数"的情况下重排整张图。
虚拟化（Virtualization）：inner_fn 里的 ops.add(a, b) 是符号化调用——lowering 阶段它返回 OpsValue 符号对象，codegen 阶段同一个闭包在 TritonKernelOverrides 下则输出 Triton 代码字符串。同一套 inner_fn 在不同 handler（V.ops）下产生不同输出，IR 定义与目标代码彻底解耦。如果你要给自研硬件写 codegen，本质就是提供一套自己的 ops handler。 
# ir.py :: Pointwise —— 一个逐元素算子就是一个 loader 闭包
def make_loader(self):
    if self.is_zero_elements():
        return partial(nop_loader_fn, dtype=self.dtype)
    return self.inner_fn      # inner_fn(index) -> OpsValue，内部用 ops.* 组合

代码 8.3 — Pointwise 的 loader 就是 inner_fn 本身；融合的本质是把内层的 loader 直接嵌进外层的 inner_fn（loader chain）。

09 · Scheduler：融合与 buffer 生命周期

Scheduler（torch/_inductor/scheduler.py）接收 graph.operations（全部 IR 节点），完成融合、拓扑排序、buffer 生命周期管理，最后驱动 codegen。它是 Inductor 里离"设备执行"最近的决策中枢。

wrap → SchedulerNode每个 IR 节点包成 SchedulerNode / ExternKernelSchedulerNode / NopKernelSchedulerNode
↓
compute_dependencies()分析 read_writes，建依赖边：MemoryDep / StarDep / WeakDep
↓
拓扑排序 + 死节点消除topological_sort_schedule() → dead_node_elimination()
↓
fuse_nodes() ×多轮贪心融合：纵向(producer→consumer) + 横向(共享读取)
↓
compute_last_usage()每个 buffer 的最后使用点 → 决定何时释放
↓

图 9.1 — Scheduler 主流程。融合前后各有一个用户注入点（_pre/_post_fusion_custom_pass）。

9.1 buffer 生命周期

这一步和你做 runtime 的显存管理直接对应：

  • compute_last_usage() 为每个 buffer 计算最后一次被读取的节点。
  • codegen 时，某节点执行完后，其 last_usage 里的 buffer 立即释放（生成 del buf / free 调用）。
  • in-place 复用：SchedulerBuffer.can_inplace() 判断能否原地改写，命中则不分配新 buffer；mutation 通过 mutation_renames 字典追踪重命名链 buf0 → buf1 → buf2。

10.1 wrapper 里的设备交互：DeviceOpOverrides

wrapper 需要 set device、拿 stream、做同步。这些设备相关的字符串由 DeviceOpOverrides 提供——这是硬件厂商最小的一块必填拼图。看 MTIA（Meta 自研加速器）的完整实现，一共就 5 个方法：

        return f"from torch._C import _mtia_getCurrentRawStream as {name}"
    def set_device(self, device_idx):
        return f"torch.mtia.set_device({device_idx})"
    def synchronize(self):
        return "torch.mtia.synchronize()"
    def device_guard(self, device_idx):
        return f"torch.mtia.device({device_idx})"
    def current_stream(self):
        return "torch.mtia.current_stream()"

register_device_op_overrides("mtia", MTIADeviceOpOverrides())

代码 10.1 — 一个真实自研加速器需要为 Inductor 提供的设备原语，就是这 5 个字符串生成器。

wrapper 生成的 device guard / stream 语句就是调这些方法拼出来的。codegen_device_guard_enter/exit()（codegen/wrapper.py）在进入/退出某 device 上下文时插入 device_guard() 与 stream 获取，kernel launch 时把 current_stream() 作为参数传进去。你的 runtime 若用 Python wrapper，只要让 torch.<yourdev>.* 这套 API 可用即可。

① 定义 — 编译期，codegen 阶段

Scheduler 驱动 backend 为一个融合组生成 kernel 源码后，通过 define_kernel()（codegen/wrapper.py:3013）把它记成一条 KernelDefinitionLine。kernel 以 <name> = <kernel_body> 的形式追加到 wrapper 模块源码里（_format_kernel_definition）。此时只是文本，还没有被执行。

# codegen/wrapper.py :: KernelDefinitionLine（wrapper IR 的一行）
@dataclasses.dataclass
class KernelDefinitionLine(WrapperLine):
    kernel_name: str
    kernel_body: str        # Triton/C++ 源码文本
    gpu: bool = True
    def codegen(self, code):        # 落成 Python wrapper 文本
        self.wrapper._define_kernel_helper(self.kernel_name, self.kernel_body, gpu=self.gpu)
    def codegen_fx(self, converter):  # 或落成 FX 图节点（见第 13 节）
        return converter._generate_kernel_definition

代码 11.1 — kernel 的"定义"是一条 wrapper IR line，既能落成源码文本，也能落成 FX 节点。

② 编译 — 编译期，异步 worker 进程池

Triton kernel 的实际编译由 AsyncCompile.triton()（torch/_inductor/async_compile.py:408）负责，并且是并行、带缓存的：

  • 先查 CompiledTritonKernels 缓存——命中直接返回已编译 kernel。
  • 未命中且有多个编译线程时，把 (kernel_name, source_code) 派发到 worker 进程；worker 里构造一个 CachingAutotuner、跑 Triton 编译，再把 kernel pickle 回主进程（TritonCompileResult）。
  • 返回的是一个 future；真正需要时 .result() 取回。
为什么设计成异步 编译（尤其 Triton→PTX→cubin）很慢。Inductor 把它扔进进程池，主线程继续生成 wrapper，最后在 AsyncCompile.wait() 处统一 join。对你的硬件 backend 同理：把耗时的设备编译放进 worker，别阻塞主编排。

③ 加载 — 编译期末尾，进主进程

编译产物通过 PyCodeCache.load(source_code) 载入成一个 Python module，从中 getattr 出 kernel 对象；Triton kernel 被包成 CachingAutotuner（携带多组 config，首次运行时 autotune 选最优 block 参数）。在 FX wrapper 路径里这一步是 FxConverter._import_kernel()（codegen/wrapper_fxir.py），它明确要求 kernel 是 CachingAutotuner。

④ 调用 — 运行时，每次前向

wrapper 里每次 launch 对应一条 KernelCallLine（codegen/wrapper.py:727），由 generate_kernel_call()（:3651）产生。它携带 call_args、arg_types、triton_meta、device 和当前 current_stream_idx：

# codegen/wrapper.py :: generate_kernel_call（节选）
device = device or V.graph.get_current_device_or_throw()
current_stream_idx = V.graph.scheduler.current_stream_idx
self.writeline(
    KernelCallLine(self, kernel_name=kernel_name, call_args=call_args,
                   arg_types=arg_types, triton=triton,
                   triton_meta=triton_meta, device=device,
                   current_stream_idx=current_stream_idx))

代码 11.2 — 每个 kernel 调用点携带的信息：参数、类型、meta、目标设备、stream。grid（launch 维度）由 autotuner 的 _interpret_args_grid 依据 block 参数算出。

生成的 Python 大致是 kernel_name.run(arg0, arg1, ..., grid=grid, stream=stream)。grid 是 launch 的线程块网格，由 tuner._interpret_args_grid(call_args, config) 依据被选中的 block 参数推出（wrapper_fxir.py:1138）。

⑤ 释放 — 运行时，用完即弃

buffer 在其 last_usage 之后由 FreeLine / make_free_by_names()（codegen/wrapper.py:4042）生成释放语句（Python 下是 del bufN，让引用计数回收显存；C++ 下是显式 free）。可复用的 buffer 走 ReuseLine 而非重新分配。整段 wrapper 结束时 generate_end 收尾。

阶段时机位置 / 接口做什么
① 定义编译期 codegendefine_kernel → KernelDefinitionLine把 kernel 源码作为文本记入 wrapper
② 编译编译期（异步）AsyncCompile.triton + worker 池Triton→cubin，带 CompiledTritonKernels 缓存
③ 加载编译期末PyCodeCache.load → CachingAutotuner载入 module、包成可 autotune 的 kernel
④ 调用每次运行时generate_kernel_call → KernelCallLine按 grid + stream 在目标 device 上 launch
⑤ 释放运行时（用完）make_free_by_names → FreeLine / ReuseLine依 last_usage 释放或原地复用 buffer

13 · WrapperFxCodegen：wrapper 即 FX 图

对"想拿 FX 图自己写 runtime"的人，这是最贴合需求的一条路。WrapperFxCodegen（codegen/wrapper_fxir.py:143）不生成 Python/C++ 文本 wrapper，而是把整个 wrapper 本身生成成一张 torch.fx.GraphModule——buffer 分配、kernel launch、free 全部变成 FX 节点。

# codegen/wrapper_fxir.py
class WrapperFxCodegen(PythonWrapperCodegen):
    """Backend to generate wrapper code as an FX IR graph."""
    def _generate(self, is_inference):
        ...
        gm = FxConverter(lines=self.lines, ...).generate()   # wrapper IR → torch.fx.GraphModule
        compiled_fn = self.compile_graph(gm)
        return FileBackedGraphModule(gm, compiled_fn), None

    def compile_graph(self, gm):
        """默认实现：直接用 eager 解释器逐节点跑 kernel。
        派生后端可 override 成真正的设备编译。"""
        return gm.forward

代码 13.1 — WrapperFxCodegen 把 wrapper IR 转成 FX 图。compile_graph 是你接管设备执行的钩子。

FxConverter（:282）遍历 wrapper IR 的每一行，通过 line.codegen_fx(self) 把它翻译成 FX 节点：AllocateLine→分配节点、KernelCallLine→triton_kernel_wrapper_mutation 高阶算子节点、FreeLine→释放。生成的 GraphModule 里，Triton kernel 通过 wrap_triton 包装、以 get_attr 挂在图上。

为什么这对你极有价值 你最终拿到的是一张可编程、可 print_readable()、可再 pass 的 FX 图，节点粒度是"分配 / launch 某 kernel / 释放"，而不是不透明的 Python 字符串。你的 runtime 只需：(1) override compile_graph(gm)，把这张 wrapper FX 图翻译成你自己的执行计划（command buffer / task graph）；(2) 通过 register_backend_for_device(..., device_fx_wrapper_codegen=YourFxWrapper) 注册。默认 compile_graph 甚至直接 gm.forward 用 eager 解释器跑，方便你先跑通再逐步接管。

注意 WrapperFxCodegen.supports_caching = False——FX wrapper 目前不参与 Inductor 的 wrapper 缓存，每次编译现生成。这在你迭代 runtime 时反而省心。

14.1 你应该在哪一层接管

路线拿到的表达适合谁
A. 自定义 Dynamo backendDynamo torch-IR 图只做推理、愿自己补 decomposition、想完全脱离 Inductor。

结语

对做硬件 runtime 的人，torch.compile 的价值不在"它能生成 Triton"，而在它把一段动态 Python 逐层收敛成了一张 stateless、functional、带完整 shape/stride/dtype/device 元信息的 FX 图，并且在每一层都留了标准注入点。你要做的，是选定介入边界（functional ATen FX 图，或 wrapper 级 FX 图），把节点解析成你自己的算子表达，把 buffer 生命周期映射成你的显存管理，把 kernel launch 映射成你的下发接口。本文给出的文件与函数坐标，足以让你照着把第一条链路跑通。

下一步可做：用一个真实完成的模型（如一层 Transformer block）走一遍 TORCH_LOGS=output_code，对照本文的生命周期表逐条核对分配/launch/free 的落点。
